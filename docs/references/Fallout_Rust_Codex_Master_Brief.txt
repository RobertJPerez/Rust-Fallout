EXECUTIVE DECISION

Build a standalone replacement runtime in Rust, loading user-supplied game data. Target Windows x64 first because that is the user's working platform and makes comparison with retail New Vegas practical. Keep portable boundaries for Linux later. The engine must ultimately play original content with original rules; visual improvements and cross-game features are optional profiles.

Start with New Vegas, then Fallout 3. Do not reconstruct Starfield first. Newer engine ancestry does not automatically implement older scripting, menus, mechanics, save behavior, or content quirks. Add Fallout 4 through a separate adapter; treat Fallout 76 as a separate service-and-runtime research effort. Selected Starfield-style mechanics can be added as optional extensions without first implementing the entire Starfield campaign.

One Rust codebase is feasible as an architectural goal. Complete 1:1 parity across all requested games is unproven and cannot be guaranteed by a prompt. This brief makes failure visible, prevents fabricated completion, and prioritizes reusable evidence. It is a research and implementation plan, not a claim that the engine has been built or that the referenced repositories have been run here.

IMPORTANT RESEARCH FINDINGS

1. Skate 3 Rust Engine explicitly credits years of prior reverse engineering and describes parity as unfinished. It is an example of the workflow, not a Bethesda compatibility dependency.
2. SugarBombEngine is an older C++ hybrid. Inspected weapon and navigation parsers skip important Fallout fields, and inspected quest code is inherited OpenMW-style code. The root CMake configuration comments out the code/src directories containing those inspected files. Trace build reachability before calling them implemented.
3. Modern OpenMW remains the major mature Bethesda replacement-engine reference. Its Morrowind success must not be confused with complete Fallout support; its official announcement describes later-game support as prototyping.
4. ByroRedux is a newly found, unusually relevant Rust/C++/Vulkan reference. Its README and feature matrix describe substantial format/rendering/runtime work. The inspected ObScript interpreter explicitly says its initial framing was derived from Oblivion and describes some calls as traced no-ops. That is a concrete reason to audit FNV semantics rather than accept “seven games supported” as campaign parity. Its license/provenance must be established per component before reuse.
5. Open Nevada (nikamigaming-create/OpenNV) currently describes a C#/Godot runtime, direct retail data loading, and a bounded FNV continuation path. It explicitly says full campaigns and complete extender compatibility are not implemented. It is different from the old OpenNV/OpenNV C# project and from 1x0DF0/OpenNewVegas.
6. Mudcrab/Wah Krah Jol provides Rust/Bevy conversion and architecture ideas. Its README has ambitious feature claims while later roadmap phases remain incomplete. Papyrus-to-Luau conversion is not evidence of faithful Papyrus semantics. Benchmark and test actual code before relying on it.
7. xNVSE, JIP LN, JohnnyGuitar, and xEdit are particularly valuable for New Vegas structures, command semantics, record formats, and behavior research. A function that calls a fixed address inside FalloutNV.exe is a hook/wrapper, not a portable implementation.
8. New Vegas uses its older compiled scripting system and XML/tile menus. Do not use Papyrus or a Flash/Scaleform emulator as the NV compatibility solution. Later games need separate script and UI adapters.

BEGIN IMPLEMENTATION CONTRACT

1. ROLE, OUTCOME, AND NON-NEGOTIABLES

Act as an experienced engine engineer, compatibility engineer, reverse-engineering researcher, and test engineer. Deliver working software in vertical increments. The deliverable is a standalone Rust application and its reusable Rust libraries, not an injected renderer, mod collection, launcher around FalloutNV.exe, or a C++ engine renamed as Rust.

The primary acceptance target is Fallout: New Vegas base game plus its official content: Dead Money, Honest Hearts, Old World Blues, Lonesome Road, Gun Runners' Arsenal, and Courier's Stash. Track base-game parity and each DLC separately. Do not shrink the scope to Goodsprings; Goodsprings is only the first end-to-end gate.

All newly authored runtime gameplay, parsers, save logic, compatibility adapters, and tooling should be Rust. Standard graphics/audio platform dependencies may contain native implementation code; enumerate them. External C++ or C# tools may be used as offline test oracles. Any native helper required to instrument the retail game must be an explicitly isolated research tool, not a hidden dependency of the replacement runtime. A pure-Rust-only restriction on every transitive dependency is not assumed; do not silently introduce a C++ gameplay engine.

Never invent file layouts, function signatures, opcode values, damage formulas, engine units, record IDs, quest stages, or native addresses. Cite pinned source or attach a reproducible experiment. Mark uncertainty as unknown. Do not fill unknown behavior with unconditional success or arbitrary default results.

Do not remove functionality to obtain performance numbers or passing tests. Fix underlying bottlenecks. Keep source data read-only and separate runtime caches and saves from retail files. User-owned data is supplied locally; do not bundle retail assets or obtain leaked commercial source. Public source availability alone does not establish permission to copy. Record licenses and provenance before copying or porting implementation code.

Read local AGENTS.md and existing architecture. Preserve user changes. Avoid wholesale rewrites of working components. Inspect actual dependencies and APIs rather than writing against remembered crate versions. Pin Rust toolchain and Cargo.lock. Implement the smallest complete dependency slice, test it, and continue.

2. WHAT “1:1” MEANS

Parity is defined against a pinned retail executable, data/DLC fingerprints, language, INI settings, difficulty, and input profile. Begin with a known supported PC installation; detect its exact version rather than assuming Steam and GOG executables are byte-identical. Store an explicit baseline manifest.

Define four independent statuses:
  A. Data fidelity: decode every required record/asset and preserve its meaning.
  B. Behavioral fidelity: scripts, AI, combat, quests, timing, and persistence reproduce observed behavior.
  C. Presentation fidelity: animation events, voice timing, UI layout, input, lighting/material intent, and camera behavior are comparable.
  D. Ecosystem compatibility: plugin load order, data mods, extender APIs, native DLL mods, and retail save import/export.

Completing A does not complete B/C/D. A running camera in a rendered cell is not “playable FNV.” Compiling a script is not executing its native functions. Parsing a physics block while skipping its collision is not physics support. A green test suite composed only of synthetic fixtures is not retail parity.

Exact pixels and physics trajectories may vary across backends. Set explicit, versioned tolerances for visual, temporal, and physical comparisons. Never relax a tolerance just to pass. Exact discrete state should match where justified; numerical comparisons must use measured absolute/relative tolerances. Preserve content-visible quirks needed by scripts, but do not intentionally reproduce memory corruption or security defects. Document optional fixes separately from the faithful baseline.

“All quests” includes intended mutually exclusive branches, failure paths, prerequisites, interruptions, companion interactions, dialogue checks, reputation consequences, and relevant save/load boundaries. Exhaustive exploration of every possible global game state is infeasible. Use a declared test universe, enumerated quest/branch coverage, risk-based interactions, and clearly stated residual uncertainty. Never claim mathematical proof of every possible playthrough.

3. SOURCE AUDIT BEFORE ARCHITECTURE COMMITMENT — M0

Produce docs/source-audit.md, sources.lock.json, docs/baseline.md, and docs/decisions/0001-runtime.md.

For each dependency/reference record: canonical URL, resolved commit SHA, language, license files and per-file notices, inspected paths, supported format/game variants, known omissions, test data provenance, build command, actual build/test result, and proposed use (dependency/reference/oracle/deferred).

Do not infer a license from a search badge. If unclear, keep the component out of copied/linked code until resolved. Do not label work “clean room” if its process does not meet that description. A project claiming to consult commercial engine source is a provenance question to investigate, not automatic approval to ingest that source.

Compare three routes in a bounded spike:
  - New Rust runtime using Bevy services and independently owned compatibility crates.
  - Reusing verified Rust components from candidates such as bsa-rs and, only after licensing/behavior audit, ByroRedux.
  - Other reference projects as external behavior and format oracles, not automatic runtime dependencies.

Default proposal: stable released Bevy for window/input/render integration; pure headless Rust simulation and compatibility crates; Rust archive reader; custom game-specific record/schema decoder; Rapier behind a physics abstraction. Choose actual versions after checking current upstream docs and MSRV. Do not launch a custom Vulkan renderer or GPU ray-tracing research project as a prerequisite for quest parity. Bevy is a replaceable service layer, not the owner of canonical game state.

M0 exit: a reproducible empty application, headless test target, baseline/data discovery with explicit missing-data reports, source audit, and one concrete architecture decision. Do not spend the entire project endlessly evaluating frameworks.

4. MODULE BOUNDARIES AND DATA OWNERSHIP

Logical module layout, split into crates when useful rather than creating dozens of empty crates:
  core_types: GameId, content namespace, FormKey, persistent instance IDs, clocks, errors.
  io_vfs: path resolution, archive access, loose files, source provenance.
  formats: ESM/ESP families, BSA/BA2, NIF/KF/DDS, audio and UI data.
  content: raw record store, schema decoding, overrides, dependency graph, asset database.
  simulation: authoritative state, entity lifecycle, events, deterministic command commit.
  script_ob: NV/FO3 compiled script decoder/interpreter and typed native-call boundary.
  rules_fnv: actor values, quests, dialogue, AI, combat, economy, minigames, survival.
  animation: skeletons, clips, controllers, event markers, blends, attachments.
  physics_adapter: units, shapes, motion, queries, character controller, ragdoll mapping.
  ui_fnv: original XML/tile semantics and native menu bindings.
  presentation: rendering, camera, audio, input devices; consumes state snapshots.
  persistence: versioned snapshots, object deltas, migrations, durable saves.
  tooling: inspect, census, coverage, trace diff, replay, benchmarking, packaging.
  game_fo3/game_fo4/game_fo76: future adapters added only when backed by concrete work.

Keep source decoding separate from canonical runtime representation. Preserve per-game extension data and raw unknown fields; do not force every game into NV's narrower schema. Canonicalization must not discard data required for behavior. Use explicit adapters and capability traits at boundaries, not hundreds of scattered if-game checks.

A FormKey identifies origin plugin plus local record identity in a game/content namespace. Never persist transient load-order high bytes as the sole identity. Stable runtime instances use separately allocated IDs; distinguish base forms, placed references, dynamically spawned references, and inventory item instances. Keep reference IDs typed, never round-trip them through f32. Persistent IDs survive entity storage reuse and cell unload.

Record definitions are immutable. Runtime changes live in instance state/delta overlays. An unloaded actor with quest significance retains authoritative state. The rendering ECS entity is not its identity. Use generational handles for transient object references and checked resolution for persistent handles.

Use contiguous component storage for hot actor/transform data and indexed immutable stores for records. Avoid Arc<Mutex<World>> as the architecture. Parsing and asset preparation can be parallel; gameplay effects commit in a stable, observed order. Record source byte offsets and origin for every decoded behavior so diagnostics can explain a failing script or condition.

5. ARCHIVES, PLUGINS, AND CONTENT RESOLUTION — M1

Implement the virtual filesystem before converting whole worlds. Discover install paths with user selection fallback. Normalize slash direction and case according to the target game's lookup rules while preserving original path bytes/names for diagnostics. Detect collisions and encoding ambiguities. Never assume all legacy filenames/text are UTF-8.

Archive handling must verify file bounds, offsets, compression sizes, supported versions, path traversal, integer overflow, and allocation limits. Read-on-demand or memory-map immutable files with documented lifetime assumptions. Decompress on bounded worker queues. Never decompress unbounded archives on the render thread.

Prototype bsa-rs/ba2 and dream_archive against the same authorized local BSA corpus. Compare listing, path hashes, extraction bytes, and error behavior against an independent implementation. Select one default backend; do not ship two redundant production stacks without reason. Pin the tested version and license; dream_archive's README explicitly distinguishes older GPL releases from newer dual-licensed versions.

For ESM/ESP implement record/group framing, compressed records, extended subrecord sizes, form references, master dependencies, deleted/disabled flags, persistent references, override chains, and game-specific version handling. Use xEdit's FNV schema and local exports as an oracle, not a blind text-to-Rust generator.

Do not merge arbitrary subfields across overrides. Reproduce target-game record and special-case merge behavior. Archive precedence is separate from plugin record precedence and can depend on configuration/invalidation rules. Build fixtures for all supported precedence rules instead of assuming “last file wins” universally.

Perform a census of every supplied official plugin/archive:
  - record and subrecord kinds, versions, counts, and sizes;
  - unresolved form references, master relationships, missing assets;
  - script command IDs, event blocks, conditions, embedded result scripts;
  - meshes, skeletons, clips, collision block types, material properties;
  - UI templates/operators/fonts and audio codecs;
  - semantic support status, not only parse success.

Unknown optional presentation data may permit a labeled inspection preview. Unknown behavior-critical data must block a faithful test, with a precise capability error. Preserve bytes for later interpretation; do not silently discard them.

M1 exit: independently verified content counts/references, deterministic override tests, bounded parsing/fuzz tests, real-data census, and a headless inspector that prints provenance. No gameplay claim yet.

6. WORLD, RENDERING, AND STREAMING — M2

Load one real interior through the production pipeline, then Goodsprings exterior. Resolve actual placed references, base models, transforms, scale, texture paths, materials, terrain, water, and lights. No procedural replacement of the Mojave in faithful mode. Debug geometry is permitted only in explicitly synthetic tests.

Establish game-to-engine axes, angle conventions, winding, and unit scale using measured fixtures. Centralize conversions. Apply the same scale to rendering, animation, physics, audio distances, navigation, and saved transforms. Rendering large coordinates may use camera-relative origins; authoritative positions remain stable in world/cell coordinates.

NIF parsing must dispatch on actual version/user-version and block layout. Validate block references and skin data. A glTF cache may accelerate rendering but cannot be the only representation of animation controllers, collision, extra data, furniture markers, or game-specific semantics. Preserve a versioned sidecar or richer intermediate representation and test fidelity.

Stream cells with explicit lifecycle states: unrequested, IO pending, decoded, dependencies ready, simulation available, render resident, unloading. Use generation tokens to discard obsolete jobs, bounded queues for backpressure, ref-counted/pinned assets for active users, and memory budgets. Never activate a cell that lacks required collision/nav data. Prefetch likely travel direction and door destinations, with hysteresis to prevent thrashing near boundaries.

Retain quest-owned actors and persistent changes when their cells unload. Separate visual residency from simulation residency and persistent existence. Door traversal must preserve activation scripts, arrival orientation, destination identity, companions, audio transitions, and save state.

Start with frustum culling, shared mesh/material caches, instancing, and suitable LOD. Profile before adding hierarchical Z occlusion or GPU-driven indirect drawing. Keep faithful materials and optional enhanced lighting as different profiles. Do not require ray tracing to run the game. A brighter modern scene is not proof of visual parity.

M2 exit: real interior/exterior traversal with correct static placement and collision, bounded streaming memory, reload stability, and tagged screenshots against matching retail cameras. Explicitly label all unimplemented simulation.

7. NEW VEGAS SCRIPTING AND CONDITIONS — M3, CRITICAL PATH

Implement the original compiled script format. Decode SCPT and embedded scripts wherever present in the pinned data schemas. Enumerate bytecode and operand variants from the corpus and compare with xNVSE, xEdit, GECK-generated microtests, and retail observations. Preserve source text when present for diagnostics; do not require SCTX to exist to execute a script.

Never replace the game's scripting system with a collection of quest-name checks or generated Rust functions for selected quests. Do not substitute Papyrus, Lua, or Luau without a demonstrated semantics-preserving translation. The initial NV interpreter should directly execute a validated representation of the original bytecode.

Typed values preserve numeric and reference behavior independently. Determine precision, integer conversion, null semantics, comparison, short-circuit behavior, variable lifetime, and expression evaluation order experimentally. Do not copy numeric assumptions from an Oblivion-derived prototype without FNV tests.

Decode once into compact validated instructions with source offsets. Use a reference interpreter first. Consider optimized dispatch or JIT only after interpreter parity and profiling show a need. Optimization must pass the same oracle tests.

Native-command registry requirements:
  command ID and name; argument signature; allowed caller context; return type;
  mutation/read behavior; observed errors; vanilla/extension provenance;
  implementation state; tests; source evidence; affected content.

Separate script statement opcodes, native command IDs, event block IDs, and condition-function identifiers. They are not necessarily interchangeable. Explicitly model owner, calling reference, target, containing object, and relevant event context.

Conditions need their own evaluator: comparison flags, AND/OR grouping, run-on subject selection, global comparison values, faction/rank/perk/actor-value queries, inventory, distance, dialogue state, quest state, and time. Reuse tested primitive queries with commands where appropriate. Never treat every unknown condition as true or false to force progress.

Quest scripts, object scripts, effect scripts, dialogue/quest result fragments, activation events, combat/death/container events, menu mode, and periodic updates require correct lifecycles and scheduling. Use explicit game/menu/real-time clocks. Do not invent the exact update order; first measure it with small instrumented scenarios.

Deterministic internal scheduling is an engineering aid, not automatic retail fidelity. Record input ticks, RNG streams/seeds where controlled, event order, and state digests. Parallelize pure reads/planning; commit effects in a reproducible sequence consistent with the compatibility profile.

Unknown command behavior produces UnsupportedCommand with game, plugin, script FormKey, byte offset, command, arguments, and caller. In developer faithful mode stop the affected scenario rather than corrupt its state. A preview mode may continue with visible incompleteness, but cannot generate a passing parity report. CPU budgets detect runaway scripts; never silently drop events to maintain frame rate.

M3 exit: every opcode/command/condition needed by the first slice is behaviorally verified, with an explicit ledger of the remaining corpus. Source-less compiled scripts work. No hardcoded quest stage advancement or traced no-ops in accepted routes.

Actor and item model:
  SPECIAL, skills, traits, perks and perk entry effects; XP/level progression;
  base/current/modifier actor values; health/AP/limbs; effects, radiation,

  Item instances retain condition, count, ownership, equipped slots, ammo,

  non-equivalent items into one stack. Leveled lists and respawn logic preserve
  their authored probabilities and persistence rules.

Quests and dialogue:
  Preserve original conditions, topic ordering/selection, speaker constraints,
  voice/subtitle resolution, greetings, goodbyes, topic follow-ups, skill checks,
  barter/repair/training services where present, result fragments, objectives,
  quest stages, start/stop/reset behavior, failure and completion distinctions.
  A SetStage-style operation may trigger scripts and side effects; it is not
  just changing a number. Save all state required to resume after interruption.
  Preserve karma/reputation/faction/disguise/crime interactions. NPC death,
  hostility, stolen ownership and companion state can alter dialogue and quests.

AI:
  Implement authored packages and conditions rather than replacing them with a
  generic behavior tree that looks plausible. Include schedules, wander,
  travel, follow/escort, use/eat/sleep, dialogue, sandbox behavior as applicable,
  combat overrides, perception, investigation, hostility, fleeing and return.
  Use source navigation triangles/links/doors where possible. Build coarse

  for the chosen costs. Funnel smoothing is appropriate for valid polygon
  corridors but must preserve jump/door/special links. Dynamic obstacles and
  local avoidance must not push actors through collision or block scripted
  destinations. Background simulation needs explicit reduced-detail semantics.

Animation and physics:
  Import actual skeletons and clips; support first/third-person variants,
  creature rigs, keyframe interpolation, bone masks, sequence transitions,
  root motion when authored, animation events, equipment attachments, face/
  lip movement, furniture interactions, hit reactions and ragdolls.
  Learn transition/event semantics from references and measurement. Do not fire
  weapon damage just because an animation started; match relevant event timing.
  A single shared humanoid walk loop is not enemy/animation parity.
  Rapier is a candidate backend, not a Havok behavioral clone. Test collision
  shape conversion, character step/slope behavior, contact/material response,
  mass/inertia, joints, projectiles, explosions, dropped objects and ragdolls.
  Keep body-part hit tests and dismemberment tied to authoritative combat state.

Combat:
  Implement weapon classes, attack/reload/jam/aim/scope states, ammo variants,
  spread/recoil, projectile/hitscan behavior as authored, thrown weapons,
  melee/unarmed, explosives, mines/traps, criticals, armor/DT/DR, limb damage,

  VATS includes target/body-part selection, displayed probabilities, AP cost,
  queued attacks, camera/time behavior, actual resolution, interruptions and
  return to real-time combat. A slowed camera overlay is not VATS parity.

UI and input:
  Implement original XML/tile tree semantics, includes/templates, traits,
  expression operators/dependencies, fonts, localization, textures, clipping,
  visibility, input focus, controller navigation and hardcoded menu bindings.
  Use a dependency graph for trait invalidation; handle cycles according to
  observed behavior with diagnostic limits. Do not assume one topological pass

  Include HUD, compass, dialogue, inventory, barter, container, repair, stats,

Audio and presentation:
  Resolve original voice/audio paths and localization. Implement spatial audio,

World systems and minigames:
  Ownership/crime, locks/keys, terminals, traps, destruction where authored,

9. PERSISTENCE IS AN EARLY DEPENDENCY, NOT A FINAL FEATURE

Build engine-native saving in the first playable slice. Snapshot authoritative
state at a defined boundary, then serialize off-thread. Use versioned chunks,
integrity checks, atomic replacement appropriate to the OS/filesystem, previous
slot recovery, and migration tests. Do not call a successful write durable until
the intended persistence guarantees are met and documented.

Persist campaign/content fingerprints, player creation/progression, reference
deltas, inventory instances, equipped state, actor values/effects, death/disable
flags, quest stages/objectives/locals, script locals and pending work, globals,
factions/reputation, timers/clocks, RNG state where owned, companions, discoveries,
respawn/merchant state and dynamic object IDs. Do not persist raw pointers or
render-ECS indices. Rehydrate from immutable content plus deltas in a defined
order; restore links before emitting callbacks that may observe them.

Test quicksave/load, cold process restart, cell unload/reload, save inside a
dialogue or combat state if retail permits it, mod/load-order changes, missing
masters, truncated saves, interrupted writes, migrations and backup recovery.
Never silently drop unsupported state on load.

Retail .fos import/export is its own compatibility track with explicit milestones.
Reliable engine-native saves do not prove retail-save compatibility. Inspect
actual save-format references and construct fixtures before claiming import.
Export to a format accepted by the retail engine requires independent round-trip
proof; it must not overwrite original saves by default. Native NVSE cosaves and
third-party DLL state are separate formats and contracts.

10. FIRST PLAYABLE SLICE — PRECISE ACCEPTANCE

Milestone target: a normal, source-driven Goodsprings route, not a debug console
teleport that manually sets quest stages.

Start a new game through the supported original opening/character-creation path.
For early development an explicitly labeled direct-cell harness is allowed, but
it cannot satisfy new-game acceptance. Resolve actual quest/record IDs from the
installed data; this document does not guess them.

Exercise Doc Mitchell's character creation, real inventory/equipment, house exit,
Goodsprings traversal, Sunny Smiles dialogue/tutorial as applicable, a live enemy
encounter, looting, a skill or dialogue condition, and a branching town quest such
as Ghost Town Gunfight/Run Goodsprings Run. Maintain separate saves for mutually
exclusive branches. Expand toward those routes as dependencies become ready.

Required checkpoints:
  - original forms and compiled scripts drive the flow;
  - appropriate voiced dialogue and UI options appear;
  - animation, collision, damage/ammo/AP and item ownership are correct;
  - quest and faction consequences match the baseline;
  - interior/exterior transitions work for player and companions where relevant;
  - save, exit the application, restart and Continue preserve the consequences;
  - both keyboard/mouse and controller can complete the route;
  - unsupported-command/condition counts are zero for accepted paths;
  - a retail-versus-replacement trace/report records what was actually compared.

A shortcut that manufactures the expected final state fails even if screenshots
look correct. No hardcoded Goodsprings exceptions as the general quest runtime.
If an authentic content-specific compatibility fix is necessary, isolate it,
explain the retail evidence, and add a regression test.

12. PARITY LEDGER, ORACLE HARNESS, AND FAILURE POLICY

Create a machine-readable parity ledger with entries like:

  id: fnv.script.<resolved-command-or-case>
  game_profile: <pinned manifest hash>
  subsystem: scripting
  requirement: <observable behavior>
  evidence: <source URL + SHA + path, or retail capture identifier>
  affected_content: <locally resolved FormKeys>
  status: unknown | decoded | implemented | unit-tested | oracle-tested | accepted
  tests: <real runnable identifiers>
  known_gaps: <explicit list>
  tolerance: <exact or measured rule>
  last_verified_revision: <actual engine commit>

Define statuses in code and tooling; a README claim cannot directly set accepted.
Aggregate by subsystem and content route. Show denominators, unknowns and blocked
tests. Distinguish unique functions from observed calls, records from semantic
fields, and parsed clips from supported transitions. Do not quote one misleading
“99% complete” metric.

Oracle strategy:
  1. Minimal synthetic plugins/scripts authored for single semantics.
  2. Execute on the pinned retail game with an isolated test profile.
  3. Capture inputs, relevant state, event ordering, screenshots/audio/timing.
  4. Run the same semantic scenario through the replacement.
  5. Compare normalized state and bounded presentation metrics.

An optional retail instrumentation helper may use xNVSE structures/hooks to
observe behavior. Keep it separate from replacement runtime. Record whether
instrumentation changes timing. Never confuse a call into retail code with an
implemented replacement native. If native tooling needs non-Rust glue, disclose
that limited research-tool exception rather than moving gameplay to C++.

Add metamorphic tests: save/load preserves observable state; different render FPS
does not change simulation outcomes outside documented retail quirks; load-order
rebasing preserves content identity; unloading/reloading preserves persistent
objects; cache rebuild yields identical resolved content; retrying interrupted
asset jobs does not double-spawn actors. Add property tests/fuzzing for parsers,
references, saves and bytecode verification. Test cycles, missing dependencies,
invalid sizes and NaN/overflow inputs where relevant.

For quest verification build a dependency graph from records, conditions and
script references. Use static extraction to identify candidate dependencies, but
account for dynamic script behavior through traces. Generate branch checklists
and state setup fixtures. Do not equate static graph reachability with actual
playthrough completion. Use interaction coverage for risky pairs such as companion
death + quest dialogue, crime + disguise, fast travel + timed script, and
save/load + pending event. Test all intended campaign ending families and DLC
routes; enumerate the remaining untested combinations.

Test hierarchy:
  - Unit: parsing/math/conditions/VM instructions with independently derived data.
  - Integration: actual pipeline from content to authoritative state and saves.
  - Differential: compare retail/reference tool versus implementation.
  - End-to-end: normal player flow, no hidden stage-setting shortcuts.
  - Performance/endurance: release builds, fixed hardware/settings, warm/cold cache.

CI without retail data runs synthetic fixtures. Private/local CI with owned data
runs corpus and gameplay checks. Missing data means SKIPPED/BLOCKED, never PASS.
Do not upload assets/saves containing retail material into public test artifacts.
Publish original fixtures, tool versions, hashes, and non-content metrics as suitable.

13. PERFORMANCE AND RUST ENGINEERING PRACTICES

Set a declared initial target such as 60 FPS at 1080p on a documented reference PC,
then measure CPU/GPU frame time, p95/p99, streaming stalls, memory/VRAM, script cost,
navigation latency and save latency. This is a target, not a guarantee. A render
benchmark with AI disabled cannot represent gameplay performance.

Separate fixed simulation stepping from interpolated rendering, while modeling
retail time-sensitive behavior explicitly. Start with a documented simulation
step and validate against retail; do not assume 60 Hz itself guarantees fidelity.
Bound catch-up work and report overruns. Do not discard time, quest ticks or
critical events invisibly. Parallel worker jobs must never nondeterministically
change gameplay decisions.

Use stable ID ordering where replay depends on iteration order. Own RNG state and
separate streams as justified; exact retail random sequences are a research target,
not an assumed property of a new PRNG. Use statistical/distribution checks for
uncontrolled random outcomes and exact tests where seeds/state can be controlled.

Algorithms and data structures should follow measured needs:
  - hash/indexed immutable record lookup with stable persistent keys;
  - dependency DAGs and cycle detection for plugin/asset prerequisites;
  - spatial broadphase/BVH or grids for queries; use backend facilities first;
  - navmesh A*, portal routing and funnel paths where appropriate;
  - bounded asynchronous IO/decompression and cache eviction with pinning;
  - snapshot plus sparse deltas for state, not copying the whole immutable world;
  - event-driven invalidation for UI/content state, plus required periodic scripts;
  - SIMD/batching only after correctness and profiling justify complexity.

Avoid premature distributed systems, microservices, GPU path tracing, a new shader
language, or an editor as prerequisites. Do not replace authored logic with LLM-
generated dialogue or probabilistic AI in faithful mode.

Rust standards: typed errors and domain newtypes; checked binary reads; explicit
ownership; safe Rust by default; isolate and document unsafe blocks; no panics on
ordinary bad user input; bounded allocations; structured tracing; cancellation;
resource cleanup; narrow public APIs. Do not create generic abstraction layers
without at least one working consumer and a clear cross-game need.

Use formatting/lints, reproducible release builds and meaningful tests. Evaluate
Miri for unsafe-sensitive units, fuzzing for byte decoders, property tests for
identity/state, and profilers for demonstrated bottlenecks. Third-party crate
choices are implementation decisions to verify against current docs, not licenses
to invent APIs. Pin dependencies and maintain third-party notices.

14. MOD COMPATIBILITY WITHOUT FALSE PROMISES

Layer A: original archives, assets and vanilla plugins.
Layer B: ordinary data/quest/asset mods using implemented vanilla semantics.
Layer C: xNVSE script functions, arrays/strings, user functions and event APIs.
Layer D: selected JIP/JohnnyGuitar/animation/UI extension APIs.
Layer E: native DLL plugins that patch the original executable or depend on its ABI.

Layer E cannot be made compatible merely by sharing command names. Original
32-bit addresses, layouts, hooks and machine code are not a 64-bit Rust API. Plan
source ports or semantic adapters; any binary-emulation route is a separate major
project. Never advertise universal NVSE DLL compatibility. A Rust extension API
should be versioned and capability-scoped; it does not automatically run old DLLs.

TTW is an explicit compatibility target with its own conversion and extension
dependencies. Audit its corpus early; gate playable compatibility on the required
NV functionality. Sections 27–34 specify the work. Do not use TTW compatibility to
claim that independently faithful Fallout 3 support is finished. Never bundle
another project's installers or data without establishing distribution permission.

17. MODERN CORE FROM DAY ONE — WHAT “MOST UPDATED ENGINE” MEANS

Build an independent modern Rust runtime. Do not describe it as Creation Engine 2
source or a complete port of Starfield's engine. CommonLibSF supplies useful type
information and wrappers, not the implementation of every referenced function.
The core should accommodate contemporary features without forcing older games
to use newer rules. NV-first is an order of behavioral validation, not a limit on
64-bit addressing, threading, rendering, input, persistence or future formats.

Use two coordinated work streams in the milestone plan (not a requirement to use
multiple agents): the primary NV compatibility path and a bounded cross-generation
architecture probe. The probe loads a small, real FO4 asset/record and a small,
real Starfield asset/record through format-specific adapters. It proves that the
core representation can preserve newer data without making complete FO4/Starfield
gameplay a prerequisite for finishing NV. Probe results must be labeled inspection
or rendering, never campaign support. Missing local FO4/Starfield data blocks only
those probes, not independent NV progress.

Modern-core requirements and acceptance:

MCORE-01 64-bit process and stable identity. No 32-bit pointer assumptions. Original
record IDs retain their exact bit patterns in their source namespace; do not cast
them into pointers or approximate floating point values. Assert all decoded sizes.

MCORE-02 Renderer capability negotiation. Define a baseline raster renderer with
portable feature requirements and optional advanced tiers. Request only supported
GPU features, expose a clear fallback, and test low/high quality with the same
gameplay. Ray tracing, mesh shaders, HDR output, upscaling and frame generation are
optional separate capabilities. Do not promise them merely because an API name
exists. Validate the pinned renderer/backend before writing integration code.

MCORE-03 Material models are explicit. Preserve legacy shading alongside FO4
BGSM/BGEM and Starfield material data. A common material interface may expose
multiple shader families; it need not squeeze every game into one PBR equation.
Texture color space, channel meaning, normal convention, alpha mode, UV transforms,
two-sidedness and vertex-color use must be explicit. Modern lighting is an optional
appearance profile; faithful appearance remains testable.

MCORE-04 Asynchronous resource scheduling. Separate IO, decompression, CPU decode,
GPU upload and readiness. Batch uploads using staging buffers/fences; never access
resources before completion. Each job carries content/version/cell-generation
identity. Bound queue depth and working memory; cancellation must release pins.

MCORE-05 Scalable world coordinates. Use a WorldAddress describing game namespace,
world/space identity, cell/region and local pose. Star-system and ship-local frames
are additional frame types, not one enormous unstructured f32 map. Preserve source
precision/units; f64 or integer-region-plus-local coordinates can be used where
measurements justify it. Convert to render-local f32 at a clear boundary. Avoid
adding astronomical magnitudes to local character positions every frame.

MCORE-06 Temporal correctness. Render FPS, simulation time, paused menu time,
animation playback time, physics substeps and wall clock are separate concepts.
Slow motion must affect the right subsystems. Support source-specific clocks and
time scaling; do not impose a universal global delta on every script and audio cue.

MCORE-07 Safe persistence and versioning. A save contains game profile, content
fingerprints, engine schema version and required capabilities. A new renderer
version should not invalidate quest state. Content cache schemas and save schemas
have independent version numbers and explicit migrations.

MCORE-08 Multi-core execution with reproducible effects. Parallelize asset work,
independent visibility and appropriate AI planning. Treat world mutations as
transactions/commands with explicit ordering constraints. Do not reorder original
script side effects merely to maximize thread count. Capture scheduling choices
needed to reproduce observed bugs.

MCORE-09 Input and accessibility. Controller, mouse and keyboard use action/context
bindings with ownership of focus and pause state. Input latency measurements count
actual simulation response; generated render frames do not count as simulation
updates. New remapping/accessibility options must not erase original menu actions.

MCORE-10 Long-term maintainability. Keep engine services, content dialects, behavior
profiles and extensions independently versioned. Modernity means measured and
maintainable architecture, not selecting every newest unstable dependency.

18. FOUR DISTINCT COMPATIBILITY SURFACES PER GAME

For each game keep four registries, with separate coverage numbers:
  FormatDialect: archive/plugin/mesh/material/animation/save encodings.
  ScriptDialect: language bytecode, data types, scheduler and native-call contract.
  BehaviorProfile: actor rules, AI, quests, combat, crafting and world semantics.
  PresentationProfile: menus, cameras, audio, authored visual/animation behavior.

These are proposed architecture names, not Bethesda API names. Design actual Rust
interfaces around verified consumers. Do not generate all four as empty traits and
claim multi-game support. A game adapter is available only when real tests exercise
its production paths.

Suggested data flow:
  User installation -> read-only VFS -> game-specific decode -> immutable content
  and preserved source metadata -> profile-aware simulation -> presentation.
Runtime deltas and script instances sit beside immutable definitions; they do not
modify decoded base records in place. Optional converted render caches preserve
source links and are rebuildable.

Create a capabilities manifest describing exactly which record families, field
semantics, script operations, animation nodes, menus and save-state categories are
supported. Keep unsupported-but-preserved data separate from implemented data.
Do not allow a loader for an unknown version to silently use the nearest old layout.

19. PAPYRUS IN RUST — FALLOUT 4, FALLOUT 76 AND STARFIELD

This is separate from the NV/FO3 ObScript implementation. Shared utilities may
include typed form identities, tracing and persistence primitives. Do not mix opcode
number spaces or assume matching instruction layouts across Papyrus generations.

Phase P0: Corpus and dialect identification.
Enumerate local PEX files, metadata versions/game identifiers, string tables,
objects/classes, inheritance, states, properties, variables, functions, instructions
and native declarations. Cross-check against Champollion, Caprica and source scripts
provided by the installed tools where legitimately available. Preserve byte offsets,
debug information and exact source hashes. Never require proprietary script sources
to be checked into the repository.

Phase P1: Verified decoding and linking.
Validate operand counts/types, instruction bounds, branch targets, class/property/
function references, inheritance and imports. Handle cyclic object graphs safely;
reject malformed data with source context. Keep a raw representation plus validated
executable form. Decompilation is a debugging aid, not the runtime's authoritative
execution format. Source -> compiler -> PEX -> decompiler -> source round-trips can
expose defects but do not alone prove semantic equivalence.

Phase P2: Values and dispatch.
Represent actual per-dialect primitive/reference/array/structure types where
supported, including null/None, casts, property getters/setters, inheritance, state-
specific methods, method resolution and default values. A newer dialect's types
must not be accepted in an older profile without evidence. Derive numeric widths,
overflow, string behavior and array mutation semantics with compiler/runtime tests.
Keep engine object handles distinct from VM object instance IDs and array IDs.

Phase P3: Continuations and scheduling.
Implement stacks, frames, locals, argument binding, event dispatch, suspended calls,
latent returns, timer registration, cancellation and object unbinding. Model an
engine call as a typed outcome such as completed, suspended with a token, or failed;
these are proposed Rust outcomes, not guessed native ABI constants. A sleeping
script must resume with its state intact, not restart its function. A budget-exceeded
script stays pending according to the supported scheduling semantics; it is not
deleted. Study per-object ordering/locking and observed concurrency rather than
assuming a single FIFO queue perfectly matches retail.

Phase P4: Native API host.
Maintain a versioned registry for each script class/function signature, defaults,
caller restrictions, result type, side effects, latent behavior, event emissions and
test evidence. Separate a Papyrus native from a C++ engine method and from an F4SE/
SFSE extension. A native stub returning zero is not a supported API. Generate
coverage from actual referenced natives in the local corpus and from live traces.
Implement by dependency priority while keeping the complete remaining list visible.

Phase P5: Game systems connected to the VM.
Bind real actor/object state, quest aliases, scenes, packages, dialogue, location,
inventory, workshops, audio, animation requests and input. Use original script
logic and authored records. Quest alias filling must implement conditions and
selection rules; it is not a preselected list of named NPCs. Story/radiant events
need their actual dispatch and matching semantics. Block a scenario when an
unsupported binding affects its result.

Phase P6: Serialization and reload.
Save object instances, properties, arrays/structures, active/suspended stacks,
event registrations, timers, latent tokens and object links. Define safe snapshot
boundaries and how waiting engine operations are restored without duplicate effects.
Resolve links before callbacks. Test a latent movement/animation/timer operation
across save/load, object unload and process restart. Do not serialize OS threads,
raw pointers, or compiler-specific Rust layouts.

Phase P7: Compatibility sweep.
Run generated semantic microtests and representative authored scripts against each
retail game profile. Report parse coverage, instruction coverage, native binding
coverage and end-to-end outcomes separately. A mature Skyrim PEX VM can inform the
design but cannot certify FO4 or Starfield behavior.

Source reading targets:
  libxse/commonlibf4 include/RE/B/BSScript_IVirtualMachine.h and
  include/RE/B/BSScript_Internal_VirtualMachine.h;
  libxse/commonlibsf include/RE/I/IVirtualMachine.h and
  include/RE/V/VirtualMachine.h;
  Orvid/Caprica compiler/game options and PEX code;
  Orvid/Champollion PEX readers;
  skyrim-multiplayer/papyrus-vm and the active VM path inside skymp.
Verify every path/revision. Headers describe interfaces/state; abstract methods and
relocated calls still require independent implementation in our standalone runtime.

20. FALLOUT 4 — DETAILED IMPLEMENTATION AND ACCEPTANCE

FO4-A Baseline and records.
Pin exact executable/content versions, including updates and DLC. Detect record
and archive versions independently; never select an entire parsing dialect from a
marketing label such as next-gen. Extend identity resolution for supported plugin
indexing schemes and test against xEdit. Decode VMAD script attachments/properties,
quest/scene/alias data, packages, items, modifications, recipes and workshop records
as documented by the exact schema. In-memory CommonLib layouts are not on-disk
ESM layouts; keep those definitions in different modules.

FO4-B Materials and geometry.
Implement BA2 generic/texture handling, required NIF structures, BGSM/BGEM material
versions, skinning/partitions, material swaps, decals and relevant shader features.
Use Material-Editor, nifly/PyNifly, NifSkope and fo76utils for independent inspection.
Build fixtures for opacity, normals, emissive, wetness and layered/custom cases
actually found in the corpus. Rendering a diffuse texture on every object does
not satisfy material fidelity.

FO4-C Precombined geometry and visibility.
Audit precombined mesh membership and relevant authored visibility data. Decide
whether to consume supported original data or generate our own render clusters.
Either route must retain each reference's identity, enable/disable state, material
override and collision/activation role. Keep a mapping from cluster ranges to
source references. An object disabled by a quest cannot remain visibly welded into
a cached combined mesh. Invalidated regions must rebuild or fall back locally;
do not solve one changed reference by permanently disabling all batching.
Conservative visibility fallback must avoid hiding visible content. Replacing
original visibility algorithms is acceptable only when scene correctness is kept
and performance is measured. Never use stale visibility data from another load order.

FO4-D Animation/behavior.
Treat skeletons, compressed clips, character/project bindings, behavior graphs,
ragdoll mapping and physics as distinct data. Enumerate actual Havok layouts and
node classes from owned files. Implement supported readers plus a runtime for
required state machines, blends, generators, modifiers, conditions, bindings,
annotations and event ordering. A graph editor is not a behavior evaluator; a pose
preview is not locomotion/combat integration. Use BGS, hkxpack, PyNifly and F4 OAR
to understand structures, with their limitations and provenance retained.
Test humanoids, creatures, power-armor variants, first-person weapon rigs, paired
interactions and interrupted transitions. Clip duration, additive reference pose,
root movement and event markers must survive conversion. Do not flatten graph
semantics into one clip-name-to-animation lookup table.

FO4-E Power armor and modular equipment.
Represent the frame, attached pieces, piece condition, actor attachment, entry/
exit sequence, power use, UI and movement effects as connected state. Test entering,
exiting, losing a piece, damage, depleted power, save during supported transitions,
NPC use and ownership. Modular weapons need attachment slots, compatibility rules,
instance data, effective stats, meshes, animations and resource consumption. A
workbench option is unavailable if its prerequisites are not actually satisfied.

FO4-F Workshop settlements.
Create transactional placement validation: recipe/perks/material availability,
build boundary, collision/support/snap requirements, preview, commit, cancellation
and refunds/scrapping. Match baseline consumption order and ownership. Placement
preview must never consume materials or alter the world before commit.
Model power nodes/links/components explicitly. A simple connected-component traversal
can serve initial graph recomputation; splits/deletions need recomputation or a
correct dynamic-connectivity strategy. Union-find alone cannot handle arbitrary
edge deletions. Power availability and radius distribution must follow observed
game rules, not general electrical circuit assumptions.
Preserve object assignments, beds/resources, settlers, population, production,
supply links, attacks, happiness and timers as applicable. Schedule background
updates using game-time semantics and reconstruct them after unloaded periods.
Do not invent production formulas. Separate placement/native behavior from the
original Papyrus workshop scripts so both participate in execution.
Test build -> assign -> connect power -> leave -> wait -> return -> save -> restart
-> inspect, including removal of a power link and a moved/scrapped assigned object.

FO4-G Dialogue, quests and actors.
Implement scene phases/actions, voiced protagonist choices, interruption/re-entry,
camera changes, alias lifecycles, story events and companion affinity. Test ordinary
dialogue and combat interruption. Quests must resume after the player leaves and
returns. Radius triggers, actor packages and script ownership cannot be replaced
with stage-name-specific timers. Support faction consequences, settlement/radiant
content and companion-specific reactions through original data.

FO4-H UI, audio and progression.
Audit the actual menu/movie formats and native data-binding protocol per movie.
Evaluate Ruffle against real files rather than assuming all Scaleform extensions
work. Provide required native host callbacks and game-to-menu state updates.
Data-only conversion to generic widgets is not equivalent to original menu logic.
Preserve Pip-Boy, perk chart, crafting, workshop, VATS, dialogue, maps, radio,
container transfer and settings functionality on both input methods. Include
survival-mode-specific save/travel rules and progression distinctions in profiles.

FO4 exit sequence:
  F4-0: corpus/format audit and material gallery.
  F4-1: one interior and exterior with actor animation/collision.
  F4-2: Papyrus native calls, aliases and a real branching dialogue/quest.
  F4-3: combat, looting, modifications and power armor, with cold Continue.
  F4-4: settlement placement/power/assignment loop survives unload and restart.
  F4-5: supported new-game opening, main faction routes, companions and side content.
  F4-6: each DLC/workshop pack independently tested, then integrated.
  F4-7: performance/endurance, data mods, optional extender APIs and release gates.
Use original-form discovery for route selection; do not guess FormIDs in this brief.

21. STARFIELD — FORMATS AND ENGINE-SERVICE RESEARCH

Treat Starfield support in three levels:
  SF-I: inspect/import/render verified content and preserve its semantic metadata.
  SF-F: optional selected mechanics adapted into a Fallout expanded profile.
  SF-C: complete Starfield campaign compatibility, a separately accepted future scope.
Delivering SF-I must not be advertised as SF-C. The current request justifies detailed
research and planning for all three, but NV completion must not be blocked by SF-C.

SF-A Records, archives and materials.
Inspect the installed version's ESM/plugin indexing and BA2 variants. Use updated
xEdit definitions and independently tested Rust archive readers. NIF references may
lead to external geometry and material resources; follow the full graph rather than
treating every NIF as a self-contained mesh. Preserve origin and fallback decisions.
Investigate BSGeometry, .mesh, material .mat references and compiled component-
database data using Starfield Geometry Bridge, the Starfield Blender extension,
fo76utils/NifSkope and Gibbed's component-database code. Implement actual versioned
formats; do not infer structures solely from a file extension.
Material resolution needs identity, inheritance/components, overrides and texture
roles. Use cycle detection and memoization for a dependency graph once those
relationships are verified. A missing required parent/component must be a clear
unsupported state, not a generic gray material counted as success. Keep authored
material data separate from an evaluated shader representation so later fixes do
not require reparsing every archive. Test the measured precedence of local/modded
materials versus database definitions.

SF-B Geometry, morphs and collision.
Enumerate vertex/index layouts, external mesh versions, LODs, skinning/morph data,
bounds and collision references. Validate index bounds, quantization, transforms,
normal/tangent interpretation and skeleton mappings. Use reference tools to compare
bounding boxes, vertex counts, shape topology and selected rendered views. An
exporter supporting a subset of assets is not a universal importer/runtime.
If using meshlets, preserve a conventional indexed-draw fallback; meshlet generation
and GPU mesh-shader support are different capabilities. Do not require hardware
features that the selected Rust renderer cannot reliably expose.

SF-C Animation graphs are not FO4 HKX behavior graphs.
The inspected Starfield Behavior Editor documents .agx and an in-house behavior
solution; CALUMI.Motion also targets .agx and lists additional rig/animation work
separately. Build a Starfield graph importer and evaluate actual node semantics,
state transitions, variables, events, conditions and bindings. Identify the local
clip/rig/auxiliary formats independently; no assumption that a FO4 .hkx decoder
solves the entire animation stack. Shared pose blending/math is reusable only after
per-format interpretation is correct. Keep node coverage and transition/event
coverage visible separately from file parsing.

SF-D Planet surfaces and procedural content.
Define addresses for stellar system, planet/body, orbital region, surface region,
interior and ship-local frame as necessary. Use the original records and reproducible
surface inputs where available. CommonLib planet/surface type declarations expose
some structure but do not provide a complete procedural-generation algorithm.
If exact generation behavior is not recovered, mark surface parity blocked; do
not silently substitute a procedural terrain generator with similar biomes.
Record seed inputs, generated-region identity, persistence, landing-site selection,
resource/scanner data, weather/environment and revisit behavior. Source-authored
locations and generated placements must retain distinct identities.

SF-E Space and ship topology.
Separate ship assembly, interior room/door topology, local reference frame, flight
body, inventory/cargo, crew assignment and persistent ownership. A ship-builder
prototype needs attachment/compatibility validation, bounds/collision, connectivity,
placement transactions and regeneration of affected topology. A visually assembled
ship with inaccessible habs is not complete.
Flight needs independent verified handling, propulsion/power allocation, shields,
weapons/targeting, docking, boarding, transitions and relevant AI. Handle a dock/board
transition as a versioned world-state transaction so crew/cargo/player positions
do not duplicate or disappear. Source behavior may use discrete transitions; do
not claim seamless planet-to-space flight is required by or inherited from the game.

SF-F Gameplay and UI if full support is pursued.
Implement the Starfield Papyrus dialect/native APIs, scene/dialogue/quest systems,
skills/challenges/research, companions/crew, boosts/gravity/environment, equipment,
scanning/surveying, outposts/resources, ships and crime/factions. Inventory and menus
must represent each system's authoritative data. Outposts are not automatically
FO4 settlements with new meshes; share primitives but verify rules separately.
Quest resets/NG+ or other campaign-wide state changes require a reset policy for
persistent objects, player/meta progression and imported content. Enumerate exact
reset/preserve behavior from the target build rather than guessing it.

SF exit sequence:
  SF-0: installation/build fingerprint and source/tool capability audit.
  SF-1: real interior -> external geometry -> materials -> collision, with reports.
  SF-2: actor rig/clip -> .agx behavior -> movement and interaction -> cold Continue.
  SF-3: compiled script -> native host -> voiced dialogue -> real quest consequence.
  SF-4: bounded surface, scanning, resource and outpost persistence tests.
  SF-5: a ship interior/flight/dock/board/cargo/crew persistence route.
  SF-6: full campaign and expansion matrices only when the user pursues SF-C.
Every level keeps unknowns visible; a data viewer cannot unlock a campaign badge.

22. CONFORMANCE TESTS THAT CATCH THE MOST LIKELY IMPLEMENTATION ERRORS

These are proposed test cases, not claims they have already been run. Add precise
fixtures, expected values and source evidence during implementation. Keep tests
independent of implementation logic; do not compute expected output with the same
function being tested.

CORE-IDENTITY-01: load two plugins with the same local record ID in different
namespaces; override one; reorder unrelated plugins; save/reload. Objects must
retain correct identity, source provenance and state without aliasing.

CORE-STREAM-02: start an asset job, leave the cell, return after a newer request,
then complete the old job. No stale spawn, double actor or leaked resource pin.

CORE-TIME-03: repeat an observed input sequence at 30/60/120/144 render FPS and with
simulated short stalls. Compare elapsed game time, firing cadence, animation events,
script results and menu pause behavior using declared tolerances. A capped 60 FPS
test alone does not prove render/simulation decoupling.

NV-SCRIPT-04: compile equivalent microtests with source text present and absent;
execute arithmetic, reference access, conditional control flow, events and native
calls. Results agree with retail, including failure/null cases.

NV-CONTEXT-05: execute a condition with subject/target/reference contexts that
produce different answers. Verify AND/OR grouping, operand type and comparison
source. This catches “all conditions run on player” implementations.

NV-INVENTORY-06: two visually identical weapons with distinct condition/ownership/
modification data are transferred, equipped, dropped and reloaded from a save.
No instance-state loss or improper stack merge.

NV-QUEST-07: complete an intended branch, fail another branch, interrupt dialogue,
kill or disable an eligible actor where allowed, leave the area and cold Continue.
Compare quest stages, topics, faction changes and objectives to retail. No debug
stage setters may occur in the accepted player route.

PAPYRUS-LATENT-08: a script awaits a native action; save; quit; reload; complete or
cancel the action. Exactly the correct continuation resumes, without duplicated
rewards or lost locals/event subscriptions.

PAPYRUS-LIFETIME-09: script references an unloaded or deleted object, holds arrays
and aliases, receives events and later unbinds. Match observed null/lifetime and
registration behavior; do not dereference expired Rust entity slots.

FO4-WORKSHOP-10: build a generator/link/consumer and assign an actor. Remove a middle
link, move an object, unload, advance time, return and reload from disk. Observe
correct power split, assignment, resources and object state, not just wiring visuals.

FO4-PRECOMBINE-11: a scripted reference is hidden/changed in a combined region.
Correct geometry disappears/changes, collision and activation agree, unrelated
geometry remains, and the optimization rebuild stays bounded.

FO4-ANIM-12: interrupt reload/attack with a state change and a camera change. Ensure
ammo, damage, audio and animation markers occur at the correct counts/times.
Test distinct compression/graph types rather than one successful humanoid clip.

FO4-ARMOR-13: enter and exit power armor, change/damage a piece, deplete power,
leave/revisit the frame and cold Continue. Ownership, attachments and player state
must agree; no duplicate frame or permanently applied effect.

SF-MATERIAL-14: two objects reference shared material data with different instance
overrides. Resolve inherited/overridden components and textures; no cross-instance
mutation or material cache collision. Missing required data blocks faithful rendering.

SF-GEOMETRY-15: resolve a NIF with external .mesh data across archive/mod precedence.
Verify correct bounds/LODs/collision and produce an actionable missing-dependency
error when one required member is removed.

SF-GRAPH-16: an .agx state change selects/blends clips and emits animation events.
Test repeated events, interruption, save/load and unsupported node reporting. File
import/export success is not sufficient for this case.

SF-FRAME-17: walk inside a moving/docked ship or equivalent validated reference
frame, transition through a door, save and reload. Local pose, world pose, gravity,
audio and collision must remain consistent without floating-origin drift.

SF-TRANSFER-18: interrupt a supported dock/board/travel operation before and after
commit. Recover one consistent player/crew/cargo state with no duplicated items.

ALL-FAULT-19: corrupt a cache/save chunk and remove a dependency. Diagnose the actual
missing/corrupt input, retain prior good saves, and never overwrite retail content.

ALL-COVERAGE-20: intentionally invoke an unimplemented native/condition/graph node.
The runtime emits an unsupported capability, and the acceptance report cannot pass.

23. IMPLEMENTATION WORK PACKETS AND REVIEW GATES

Each task is a bounded behavioral change, with these fields:
  requirement IDs; game/build profile; input fixtures; independent oracle;
  production path touched; expected result/tolerances; failure modes;
  parser/runtime/save/UI dependencies; performance budget if applicable;
  source paths and pinned revisions; validation commands; unresolved questions.

Before implementing, inspect existing code and tests. After implementing, review
actual call reachability from player input/content loading to state changes. A new
module that is never invoked is not delivered functionality. Record the test result
and update only the requirements actually verified.

Do not continually replace the engine stack when the next feature is difficult.
Architecture changes need a measured blocker, migration plan, preservation tests
and a small proven replacement slice. Bevy upgrades must be isolated from gameplay
changes unless directly required. Maintain a supported baseline toolchain instead
of following nightly or development branches by default.

Bug triage policy:
  A. Data decode/resolution mismatch: compare raw/typed forms with an independent tool.
  B. Script mismatch: compare instruction/native traces and caller contexts.
  C. State mismatch: inspect ownership, event order, clock and identity lifecycles.
  D. Presentation mismatch: compare authoritative events before tuning graphics.
  E. Performance mismatch: profile representative gameplay, then optimize the cause.
Do not “fix” a broken state transition by changing a mesh, adding a delay, skipping
an event, or disabling collision unless evidence identifies that as the actual cause.

Require a precise distinction between implemented, tested, retail-compared and
accepted. Missing prerequisites cannot be hidden by checking a box. If a function
still reaches the original executable through REL::Relocation/interop hooks, classify
it as a research bridge, never a standalone implementation.

26. SCOPE, UPDATES, AND NEXT IMPLEMENTATION SESSION

The product has one modern Rust core with separately measured game profiles. It
does not need to be an exact internal clone of Bethesda's architecture to reproduce
external behavior. Modern rendering, data structures and job scheduling are allowed;
changes to gameplay remain explicit optional profiles. Shared code is earned by
matching semantics, not by similar class names.

Do not silently expand “latest engine” into mobile/VR/multiplayer support, a full
world editor, new campaign writing or always-online services. Design reasonable
extension boundaries, then finish the requested game functionality. Full Starfield
campaign implementation is a future gate; selected Starfield systems can be specified
and enabled independently after NV stability.

When upstream or retail builds change, produce an impact report: content/format
differences, broken research hooks, changed native signatures, schema migrations
and failed regression cases. Keep existing supported profiles available. Do not
automatically update the user's retail installs or mass-convert their original data.

28. TTW COMPATIBILITY — DEPENDENCIES, TESTS AND MILESTONES

First create a dependency report from the chosen installation, not a hardcoded

  - New-game initialization runs once; reload never grants starter state twice.

does not validate both campaigns, and an NPC roster is not AI package coverage.

30. CONTENT IMPORT AND CONVERSION AS A REPRODUCIBLE RUST BUILD PIPELINE

This section proposes our architecture. It is not a description of TTW or Tales
From Appalachia internals. Share this machinery across games without assuming
their source formats or gameplay rules are interchangeable.

Support two inputs to the same runtime:
  A. Original game data -> game-specific reader -> preserved semantic representation.
  B. Known converted content -> converter-specific reader/profile -> representation.
Both feed the shared runtime with explicit game/profile semantics. Do not force
everything through NV or FO4 export formats. A lowest-common-denominator format
can permanently discard information that the Rust runtime could otherwise retain.

Use distinct identities for source game, content namespace, plugin, local form,
installed version and dynamic runtime instance. Namespace plus plugin/local form
identifies a record; the content-version fingerprint validates its definition.
Do not turn every asset rebuild into a new gameplay identity. Record import history
and use explicit migrations when the actual identity changes.

Proposed pipeline stages:
  1. DISCOVER: enumerate only selected installations and configured mod roots.
     Identify build/language/DLC, hashes, file sizes and archive variants. Report
     missing inputs precisely. Never overwrite the original Data directory.
  2. RESOLVE: mount archives and loose files with profile-specific precedence;
     resolve master dependencies and the effective plugin override stack.
     Preserve both winning values and their source chains for diagnostics.
  3. PARSE: decode with bounded reads and typed dialects. Keep unknown raw data,
     parser version and source location; preserving bytes does not mean supporting
     their behavior. Reject malformed critical dependencies with context.
  4. PLAN: produce a dry-run transform graph with inputs, output ownership,
     capability requirements, lossy changes and estimated storage/memory.
  5. TRANSFORM: apply versioned rules to an isolated staging area. Distinguish
     structural decoding, identity relocation, asset adaptation and rule changes.
     Do not hide gameplay changes inside a format parser.
  6. VALIDATE: check schema, links, material/mesh bindings, scripts, nav connectivity,
     collision and known semantics. Attach warnings to dependent records/scenarios.
  7. COMMIT: publish one complete pack manifest only after required validation.
     Write a durable completion marker last; recovery must ignore partial outputs.
  8. EXECUTE: run behavioral conformance against the declared reference profile.
     Successful conversion is an input to this gate, never a substitute for it.

Model transform jobs as a dependency graph. Topologically schedule acyclic jobs;
use strongly connected components to detect cyclic reference groups. Allocate
stable symbols first and resolve cyclic content links in a subsequent pass rather
than treating every cyclic world reference as corrupt. Report actual impossible
build dependencies separately from legitimate mutually referencing records.

Cache a job by its transformation version, source digests, options, target profile
and dependency digests. Use a modern content digest such as BLAKE3 or SHA-256;
check current crate documentation before selecting an implementation. Verify output
digest/length on reuse. A filename or modification timestamp is not a reliable key.
Never use a noncryptographic hash as proof that downloaded code is trusted.

Use bounded workers, bounded queues, cancellation checkpoints and per-task memory
budgets. Chunk large archives and stream where formats permit. Avoid decompressing
all games into RAM. Pin live assets, evict rebuildable caches first and prevent
cancellation from publishing half-valid packs. Persist the job journal so retries
reuse verified results, not unverified files with matching names.

Represent reference relocation with a typed mapping table:
  source namespace/plugin/local ID/type -> destination identity/type;
  transformation ID; preconditions; reason; evidence; reversibility classification.
Reject conflicting mappings, unresolved destinations and unsupported type changes.
Do not remap arbitrary byte patterns or replace textual hex strings globally.
Walk typed record fields and decoded script operands; strings only receive a rule
when their semantics explicitly require it. Follow each dialect's ID encoding.

Preserve an origin chain for every generated object. Deduplicating identical mesh
bytes is different from merging two quest objects with different gameplay identity.
Use content-addressed asset storage where useful, but never merge stateful records
merely because they look identical. Keep save-state identity stable across imports.

Audio/visual conversion rules must state their precision and intent. Preserve
original sources, animation annotations, skeleton mapping, texture channel meaning,
material alpha modes, collision units and voice timing. When Rust directly supports
a source representation, do not add a lossy intermediate conversion just because
the original FO4/NV host needed one. A measured approximation is opt-in and reported.

Distribution package: code, reproducible rules and permitted fixtures. Local build
outputs may contain game content and stay local by default. Audit source licenses
before incorporating code; public visibility is not permission to redistribute
everything in a repository. This is a provenance requirement, not a claim that
owning both games automatically grants every form of redistribution permission.

31. CROSS-CAMPAIGN IDENTITY, TRAVEL AND SAVE MIGRATION

TTW compatibility should follow TTW's measured transfer rules. Unified-crossover
needs a separate explicit policy. Do not automatically apply the custom crossover
transaction model as a claimed description of TTW's implementation.

Each campaign owns quests, world changes, time rules and persistent actors. A
shared traveler may carry transferable state, but campaign state remains namespaced.
Specify the policy for every item/stat/perk/companion category: carry exactly,
translate with a reversible mapping, store in source escrow, or deny transfer with
a reason. A FO4 weapon modification graph cannot silently become an NV weapon with
the same display name. An unsupported companion must not become a generic actor.

Track transfer identity, source snapshot, destination snapshot and policy version.
Within one local transactional store, commit all related changes atomically. If
worlds use separate save stores, use a durable journal and recovery protocol with
idempotent operations. Do not claim two filesystem renames on separate files are
one atomic transaction. Handle disk-full and power-loss failures explicitly.

Recovery invariants:
  - exactly one active traveler authority after recovery;
  - inventory represented exactly once across active state and explicit escrow;
  - transfer rewards and quest callbacks execute at most once;
  - retrying the same transfer ID cannot mint items or replay introduction quests;
  - source and destination campaign deltas remain recoverable;
  - no new campaign is marked available solely because its map was imported.

Save header should record runtime schema, game/profile ID, content-set fingerprint,
behavior policy version and migrations applied. Validate it before loading objects.
Keep original saves untouched. Native Rust saves, retail-save import and cross-profile
migration are three separate deliverables with separate evidence requirements.
When a profile changes incompatibly, explain why migration is blocked; never discard
unknown quest state to force a save to load. Back up before a supported migration.

32. FALLOUT 76 ACCEPTANCE — LOCAL DATA, GAMEPLAY AND SERVICE BEHAVIOR

Conversion research raises confidence in some content paths. It does not establish
where every quest's logic lives. Determine that from the selected build and specific
features. Do not assert “all scripts are server-only” or “all behavior is in client
files” without evidence. A named quest record, objective text or terminal entry does
not by itself supply trigger, reward, scheduling and persistence behavior.

Create a feature-by-feature evidence table with these origins:
  local declarative data; local compiled logic; native host behavior;
  measured service-dependent behavior; inferred behavior; unknown.
Record client build, observation date, content pack and dependencies. Distinguish
what a converter reconstructed from what original data directly represents.

Progress ladder for the selected FO76 content baseline:
  76-0: readable client corpus, dependency map and versioned unknowns report.
  76-1: inspect/render representative world regions, interiors and assets.
  76-2: traverse those regions with correct collision, navigation and streaming.
  76-3: actors fight, animate, equip/drop items and persist under specified rules.
  76-4: a genuine quest branch completes with conditions/rewards and cold Continue.
  76-5: enumerated campaign, side-content and event scenarios pass, including reset,
        interruption, instancing and persistence. Report unresolved service gaps.
  76-6: full declared release matrix and long-run verification; no blanket claims
        about retired or future content outside the pinned scope.

Treat offline adaptation and original online parity as different profiles. For
offline adaptation, specify scheduling, difficulty, event participation, loot,
vendors, crafting unlocks and reset rules; mark deliberate changes clearly. Keep
an internal authoritative-state boundary so later networking can reuse the rules,
but do not make multiplayer infrastructure a prerequisite for the solo prototype.
For multiplayer parity, replication, parties, sessions, disconnect recovery and
authority need their own later acceptance suite. Do not hide those gaps in a map
conversion percentage. Do not use production accounts/services as a shortcut.

Require scenario evidence for an event location, an event script and an event's
actual end-to-end behavior separately. The existence of a raid room is not evidence
that encounter phases, rewards or resets work. For rewards, journal decisions and
grant operations so crashes/reloads cannot grant twice or consume inputs twice.

If an upstream converter becomes available, compare three independently recorded
paths where feasible: original observed behavior, conversion running in its FO4
host, and the Rust runtime. Differences between the first two are conversion/profile
differences; differences between the latter two may expose Rust compatibility bugs.
Do not use a converter's behavior as an original-game oracle without that distinction.

  After the required gameplay works, implement travel rules and save transactions.
  Acceptance: repeated round trips and injected failures preserve campaign quests,
  follower state, item identity and exactly-once grants. Measure TTW travel against
  TTW; measure custom crossover against its separately approved policy.

Each completed ticket must include reachable implementation, commands actually
run, observed results, unresolved limitations and the next dependency. Code review
must trace a real input to a real state/output. Synthetic tests validate mechanisms;
only declared retail/reference scenarios validate the corresponding compatibility.

34. FINAL CODEX EXECUTION DIRECTIVE

Keep the user's complete objective: a modern standalone Rust runtime for faithful
NV, then FO3 and TTW compatibility, followed by FO4 and measured FO76 expansion,
with the earlier Starfield research and optional feature path retained. A shared
runtime is not permission to erase game differences. A conversion tool is not a
substitute for the engine systems that execute the converted content.

Begin with the actual repository. Preserve working functionality, inspect its
instructions, then implement the first unmet milestone rather than regenerating
another plan. Integrate R3-01 through R3-04 with existing foundations instead of
creating a second importer beside them. Run TTW and later-game probes only when
their inputs are available, while continuing independent NV implementation.

Read and pin actual sources before using them. Never invent API calls, binary
layouts, completed features, source licenses, release availability or test results.
If a reference is unavailable, label that dependency and use the other verified
sources. Ask for the minimum missing file or environment only after completing
the independent authorized work. Do not remove scope to manufacture a green report.

The next handoff must be a runnable implementation checkpoint and evidence-backed
parity report. It must distinguish implemented, observed, inferred, untested and
blocked behavior. A full world visible on screen is a valuable milestone; all quests,
enemies, animations, features and saves working is a separate, much larger claim.

RESEARCH LIMITATIONS AND WHAT CODEX MUST VERIFY NEXT

This brief reviewed primary repository descriptions/docs, current metadata for
many candidates, directory trees, and selected actual files. It did not clone/build
all repositories, benchmark them, inspect every license, or execute retail games.
No official complete source release for the requested modern Fallout engines was
established by this research. Most useful public sources are community tools,
reverse-engineered interfaces and incomplete replacement implementations.

Some current repositories are moving quickly and their names/status/docs differ
across mirrors. Pin revisions at implementation time. Claims such as “100% parse,”
“seven games supported,” “all scripts compile,” and “60 FPS” need their actual
denominators, configuration and reproducible evidence. Do not repeat them as full
campaign support. Current repository descriptions are not substitutes for tests.

The first implementation session should therefore produce the source audit and
baseline, build the Rust application and data inspector, then implement the first
verified format/behavior dependency. The long-term target remains full NV fidelity
and the multi-game roadmap above, with scope preserved and progress measured by
observable behavior.
